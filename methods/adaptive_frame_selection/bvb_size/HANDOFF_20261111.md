# Object-size handoff: joint reference reconstruction and in-situ views

This checkpoint archives the November 10 object-size work before the focus moves to room size. The older `render_size.py` extraction prototype stays intact. The new `in_situ.py` keeps objects in the reconstructed scene. These are separate experimental routes, not a claim that the latest route wins on all questions.

## What is implemented

1. Review cached candidate groups using `prompts/reference_review.txt`. Confirm the actual target, choose a co-visible reference whose useful dimension has visible endpoints, and record uncertainty. Unknown exact size is not a reason to reject an otherwise useful reference; it is also not a measured scale. Tiny/distant or fabric-obscured references are discouraged. This semantic review requires a model or a human; the camera solver itself is pure computation.
2. `handoff.py joint` packages **all frames of that selected group**, hashes and shared poses, target/reference roles, colors and instance limits. It appends the reference rules to a caller-supplied clean upstream reconstruction template. Original cached detections/poses may be reused. This is the same-frame extension of the V10 joint reconstruction route (upstream `5e2355e157`), not an unmodified full V10 frontend replay.
3. `in_situ.py` searches a common camera first; if it fails acceptance, it searches two views with matching orientation, focal length and distance to the respective object centers. It uses continuous coordinate descent with step shrinking and an existing-camera initialization fallback, not a fixed camera grid, Powell, or a guaranteed global optimum.
4. `handoff.py qa` prepares either rendering-only or rendering-plus-original-frames requests. It correctly describes one versus two renders and identifies red target / green reference. It neither calls a model nor logs in to an account. Use the separately configured subscription/API runner; the experiment used Pro Astra High, one call per arm, no automatic retries.

## Camera behavior and limitations

- All meshes with `role == "target"` and the requested `category` form one complete object. Upstream must tag every component correctly. It does not infer nouns or repair missing meshes.
- Source positions, rotations, scales, mesh visibility and the source `.blend` are unchanged. Walls and floor remain; there is no automatic removal of walls. The output is images and `result.json`, not a modified source blend.
- Bounding-box projection checks clipping and minimum image footprint. First-hit triangle-sample rays check environmental obstruction and some identifiable surface coverage.
- When the two object bounds touch/overlap, mutual occlusion may be allowed while requiring some own-object surface. This supports table/laptop and bed/blanket, but bounding-box contact is only a heuristic, not an exact physical contact test.
- One accepted image is preferred. The paired branch uses matching camera settings, but perspective depth within each object and differing semantic fronts can still impair comparison.
- `mode: unresolved` renders diagnostic images only; the QA preparer rejects them. Even `single`/`pair` needs human visual review: geometric acceptance failed to detect some walls/identity problems in the pilot.
- The archived latest renderer neutralizes scene light intensity in memory, uses material colors and CPU Cycles (two threads). This normalization was introduced for a lighting failure; it does not calibrate geometry. Use server-side Blender, not a local GPU workload.

## Run

Run from `methods/adaptive_frame_selection`. Python preparation requires only the standard library. Rendering requires Blender (experiment: 5.3 beta; other versions were not rerender-tested for this extraction).

```sh
python -m bvb_size.handoff joint \
  --evidence /data/case/evidence.json --decision /data/case/decision.json \
  --base-prompt /data/upstream-clean-system-template.txt \
  --out /data/package --runtime-root /runs/case
```

Evidence schema: `question` contains public `id`, `scene`/`scene_name`, `question`, `question_type`, `objects`; `frames` contains `group`, relative `file`, `sha256`, `timestamp_s`, `source_frame_index`, `c2w_blender`, `intrinsics_640x480`, and `compact_camera`. Optional `shared_pose_sources` preserves upstream provenance. Decisions are the JSON object requested by `reference_review.txt`, not a raw provider envelope. Do not supply GT, previous answers or credentials in the base template or decision. Question answer fields are excluded by an explicit whitelist.

The package's `input.json` and `system-prompt.txt` feed the caller's joint reconstruction runner. Pass each frame as an image with its corresponding camera information; do not submit file paths as if the model could read them. Deploy the copied frames under `--runtime-root`, then build generated code using the existing isolated Blender execution environment. This package deliberately does not execute untrusted generated Python or replace the upstream reconstruction runner.

The upstream frontend adaptation required `payload.scene` derived from `scene_name` and rejection of mixed-scene input. This checkpoint does not patch upstream V10 or claim to rerun DINO/LingBot. Use compatible validated upstream inputs.

```sh
blender -b -t 2 --disable-autoexec --python-exit-code 1 \
  --python bvb_size/in_situ.py -- \
  --blend /runs/case/scene.blend --target table --reference laptop --out /runs/case/views

python -m bvb_size.handoff qa --joint /data/package/input.json \
  --views /runs/case/views/result.json --out /data/render-only-request.json

python -m bvb_size.handoff qa --joint /data/package/input.json \
  --views /runs/case/views/result.json --include-frames --out /data/mixed-request.json
```

Both paths require distinct target and reference categories; same-category instance comparisons need a different instance-key interface. Red/green materials must already be assigned by the joint reconstruction; the renderer preserves them, and the prompt preparer does not independently verify colors. Visually inspect target identity, complete extent, reference boundary and obstruction before sending QA. `visual_review_required` is an explicit reminder, not an automatic semantic approval.

## Results and stopping decision

The compact `experiment_checkpoint.json` includes the sofa/table/blanket pilots and all four expansion cases, including the two no-QA view failures. Historical 0.125-FPS attachment baselines lacked full model/effort receipts and are labeled accordingly; do not present them as a fully controlled same-protocol replication.

The four-case expansion did not justify scaling up: cutting board (2340) and TV (2356) failed visual review and were not sent to QA. Among the two QA-ready cases, rendering-only MRA was 68.18%, mixed-input MRA 90.91%, versus historical baseline 95.45%. On all four attempted cases, assigning failure-zero **only as a pipeline diagnostic**, these become 34.09% / 45.45% versus 81.82%; missing QA itself is not a numerical prediction of zero. No broad superiority is established.

Earlier 81.82% on 20 questions selected the higher-scoring reference/no-reference arm per question. That is an oracle-style paired-trial summary, not this automatic method's benchmark score. Old category priors and no-reference rules remain archived in `priors.json`; the new in-situ entry point explicitly takes a reviewed pair and does not silently apply per-question best-score choices.

No room-size code, images, videos, blend assets, model weights, credentials, tokens, account emails or personal server locations are published here.

## Validation

```sh
python -m unittest bvb_size.test_policy bvb_size.test_handoff
python -m bvb_size.handoff --help
```

Tests cover existing policy, preservation of poses and image hashes, public-question filtering, rejection of absent boundary evidence, rejection of unresolved views, and paired-image/original-frame prompt ordering. The camera algorithm is copied from the previously rendered neutral-lighting experiment (docstring clarified only); this publication does not rerun expensive rendering or QA and does not treat unit tests as visual validation.
